# 「播报没来」判定树

用户说「今天没收到播报」「昨天的播报怎么没来」时，按这棵树走，不要跳步，也不要一上来就猜是网络问题。

## 第一步：状态快照的日期是不是今天

```
state == null
  └─ 从未成功运行过 → 不是漏跑，是压根没跑起来。查服务是否起来、cron 是否安装。
state.date == 今天
  └─ 今天跑过 → 跳到第二步。
state.date == 昨天及更早
  └─ 今天没跑完 → 跳到第三步（是触发问题，不是签到问题）。
```

判据只看 `state.date` 和系统当天日期，**不要**用 `log_tail` 的时间戳代替——日志可能是跨天的。

## 第二步：今天跑过了，那播报为什么没到

跑到 ≠ 推送到。按这个顺序查：

```
state.finished 是否存在
  ├─ 缺失 → 运行中途崩了，日志尾部找 Traceback / abort。
  └─ 存在 → 继续。
attempts.checkin[-1].ok 与 attempts.travel[-1].ok
  ├─ 有 false → 播报里标了「存在失败，见下」，是内容里写了失败，不是没发。
  └─ 全 true → 继续。
推送环节
  └─ 查企业微信机器人 webhook 返回值。失败时服务会重试，三次都失败会在日志
     留下明确一行。这种情况播报确实没到，但签到是成功的。
```

关键结论要先说清：**签到成功但播报没到，和签到失败是两件事**。别让用户以为断签了。

## 第三步：今天没跑，卡在哪一环

```
cron 有没有当天的触发记录
  ├─ 没有 → 定时任务没触发。查 crontab 是否被清、服务器是否重启过、时区是否变了。
  │          属于服务端运维问题，不在本技能范围内，直说。
  └─ 有 → 看这条记录后面有没有立即退出
        ├─ 立即退出 → 依赖缺失或配置读取失败，日志头部会有 ImportError / KeyError
        └─ 跑到一半 → 看是不是卡在重试
```

## 降级日志：`cron.<uid>.log`

如果主日志目录当时不可写，任务会把输出记到 `cron.<uid>.log`。
**看到这个文件不代表失败**，只代表「主日志没写成」。内容往往完整，直接读它就能还原当天结果。

这一点最容易误判：运维只盯 `run.log`，发现当天没有记录就判定「没跑」，实际跑了，只是写到了别处。

## 四种常见误判

| 现象 | 容易得出的错误结论 | 实际原因 |
|---|---|---|
| `run.log` 当天无记录 | 任务没跑 | 写进了 `cron.<uid>.log` |
| 播报里写「存在失败」 | 签到失败 | 可能只是旅行分支失败，签到是成功的 |
| 用户说「今天没签」 | 签到失败 | `today_checked_in` 为 true，是播报没到导致用户不知道 |
| 提示「有积分可领」 | 真有可领 | 静态文案，看 `today_checked_in` |

## 边界

以上判定只覆盖「值守服务自己有没有正常工作」。
如果是 WorkBuddy 官方接口变更、账号异常、活动规则变化导致的失败，日志里会有明确的业务错误码，
这类问题不在本技能范围内——照实说，不要硬猜。
