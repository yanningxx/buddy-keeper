### 05 作品介绍【必填·不少于 30 字】

```text
这是一个跑在服务器上的值守机器人，替你在每天 09:00 完成 WorkBuddy 里四件必须每天做、又极容易忘的事：签到、把猫猫派出去旅行并领取已到达的奖励、查看积分余额、核对成长计划还差什么。跑完之后它把结果整理成一段人话推到企业微信，人在外面、不打开客户端，也知道今天签没签、猫去了哪、还剩多少积分。

目标用户是每天在 WorkBuddy 里手动签到的人，尤其是容易断签的——出差、开会、放假，机器不会忘。签到是连续扣分项，断一天，连续天数和全勤奖励一起归零，补不回来，所以这件事的代价远大于它看起来的体量。

体验方式（三步，一分钟）：

第一步，打开链接，首屏就是「值守看板」，看到的是 2026-10-29 09:00 那次真实运行的快照：今日已签、连续 4 天、累计 15 天、余额 303.3、猫已派出前往【古镇客栈】、企业微信推送 errcode 0。往下是推到企业微信的那条播报原文，以及运行日志——日志里能看到 09:00:04 有一次失败、09:01:07 重试成功，这是真实日志，没有美化。

第二步，点第二个标签「判据实验室」。这里有四组真实接口返回，点任意一个，页面左右并排给出「按按钮文案判断」和「按数据事实判断」两种结论。第一组最能说明问题：接口返回 today_checked_in 为 true，按钮文案却依然写着「立即领取」，旧逻辑据此天天误报「有积分可领」。这是本版修掉的第一个真 bug。

第三步，点第三个标签「模拟一次值守」，按「开始回放」，六步时间轴会按真实时间点点亮：任务触发、首跑失败、重试成功、旅行完成、生成播报、推送成功，全程约四秒。

核心设计四条：不拿 UI 文案当业务状态；重复执行幂等，已签到时接口直接跳过；手动补跑与定时任务撞车时用文件锁只跑一份，不会重复领取；失败按网络类和业务类分开重试，且绝不静默失败——一个每天跑但不知道有没有跑成的定时任务，比没有定时任务更让人焦虑。

技术上是 Python 3 标准库，零第三方运行时依赖；cron 触发，systemd 托管；看板是单文件 HTML；状态用 JSON 落盘，没有数据库。
```

```text
标题：我把每天点五下的活，做成了一台不用管的机器

每天都要在 WorkBuddy 里签到、把猫猫派出去旅行、看积分、看成长计划还剩什么。
单看每件都不费劲，但它们必须每天做。断一天，连续天数和全勤奖励一起归零，补不回来。

所以我写了个脚本，每天早上九点在服务器上自己跑一遍，跑完把结果推到企业微信。
出差、开会、放假都不影响，机器不会忘。

做的时候踩了三个坑，印象最深的一个：
我一开始按接口返回的按钮文案判断「能不能领」，结果天天报「有积分可领」，点进去发现没有。
查了很久才明白——那个「立即领取」是服务端下发的静态 UI 文案，已经签过了它照样返回这四个字。
后来把判据改成纯数据事实：签到看 today_checked_in，任务看进度达标 + 没领过 + 有奖励。
改完之后，播报里再没出现过假的提示。

这件事让我记住一条：不要把 UI 文案当业务状态用。文案是给人看的，状态要靠数据算。

还有个坑更隐蔽：有一段时间定时任务天天不执行，进程日志里什么都没有。
根因是日志文件被 root 建成了 644，而 cron 以普通用户跑，shell 的 >> 重定向在启动 Python 之前就失败了。
Python 根本没被启动，所以什么日志都没有。这类问题最难查，因为所有排查手段都建立在「程序跑过」这个前提上。

现在它会先探一次日志可写性，不可写就换降级文件，并把这件事本身记下来。

项目不大：Python 3 标准库，零第三方依赖，cron + systemd，看板单文件 HTML，状态 JSON 落盘，没有数据库。
但它每天早上九点真的在跑，真的在给我发消息。「真的在跑」这四个字，比任何技术选型都重要。

体验地址放评论区，需要的自取。

#WorkBuddy #1024程序员节 #自动化 #效率工具 #Python #程序员日常 #独立开发
```
